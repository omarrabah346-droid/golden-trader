# ربط Supabase قبل الاختبار الفعلي

## الجرد المحلي

- يعرّف `supabase_setup.sql` ملفات الحساب والإعدادات وبعض سياساتها. توجد تعريفات V2 في ملفات المراجعة 001 إلى 005. لا توجد نسخة محلية موثقة تطابق إعدادات الإنتاج لكل نقاط الدفع والاستحقاق.
- تقرأ الأكاديمية `purchases` و`courses` و`lessons` و`lesson_bodies` و`lesson_progress`. اعتماد الشراء في `index.html` يستعمل `aSetPurchase` لكتابة مباشرة إلى `purchases`. يستخدم عرض الإدارة `admin_purchases`.
- يقرأ التطبيق `signals` و`signal_events` ويستدعي `ai_ask` و`ai_result` و`ai_status` ووظائف `vx_marketing_*`. تُظهر الشيفرة استعمال حاويات `receipts` و`media` و`certs` و`avatars` و`partner-docs` و`entries` و`journal`. يحتاج أي اسم إضافي للتدقيق قبل الدمج.

ملف `supabase-inventory.readonly.sql` يعيد نتيجة JSON واحدة من كتالوجات التعريفات ومن إعداد خصوصية الحاويات المعروفة فقط. يتضمن الأعمدة وأنواعها، المفاتيح والقيود البنيوية وأسماء الفهارس والمشغلات والسياسات، توقيعات RPC والمنح. تتجنب الاستعلامات نصوص الدوال وتعبيرات السياسات والقيم الافتراضية وقيود CHECK النصية، إذ قد تحتوي على أسرار مكتوبة حرفياً. لا يقرأ صفوف العملاء أو أسماء ملفات Storage.

## تركيب فحص الاستحقاق

| نقطة التطبيق | ربط التحقق |
| --- | --- |
| الدروس والوسائط | اربط الدرس بالدورة داخل الخادم. افحص `academy` والاستحقاق القديم أو حق الشراء للدورة نفسها قبل قراءة المحتوى أو الترجمة `lesson_body_tr` أو الوسائط. طبّق الشرط على الاستعلام المباشر أيضاً. |
| VIP والمؤشرات | افصل البيانات العامة عن الخاصة على مستوى المورد. اربط قراءة المورد الخاص واستعلاماته البديلة بميزة `vip` أو `indicators`. |
| التسويق وAI | افحص ميزة `marketing` أو `ai` عند المدخل وفي العامل عند تنفيذ المهمة المؤجلة. افحص ملكية المخرجات عند استرجاعها. |
| RLS | اشتق الحساب من الجلسة والمورد من الصف. طبّق القيد على القراءة والكتابة حسب الحاجة، وراجع السياسات permissive الأخرى حتى لا تتجاوز القيد. الحقوق الإدارية عبر المسار الإداري المثبت. |
| Storage | حافظ على عزل الإيصالات للحساب المالك للإيصال والمراجع المعتمد. إصدار رابط للمحتوى المدفوع يحتاج حاوية خاصة وربط الكائن بالمورد وفحصه قبل التوقيع. تحقّق من صلاحية الرابط السابق حتى تاريخ انتهائه. |
| المسار المجهول | غياب استحقاق مؤكد يؤدي للرفض، وتعذر مطابقة المصدر يؤدي للمراجعة. مسارات المحتوى العام المؤكدة تبقى خارج هذا القيد. |

## تعديل الدفع القديم للمراجعة

الجزء الجاهز هو `vx_sub_v2.claim_legacy_payment` في 005. استبدال كتابة الاعتماد المباشرة يتطلب RPC واحداً يستخدم منطق الاعتماد الموجود فعلياً. هذا ترتيب المعاملة المقترحة، وتنتظر أسماء الأعمدة وتوقيع الدالة وتعريف اعتماد المالك من الجرد:

1. تحقق من صلاحية المالك على الخادم، ثم اقفل صف الشراء للتحديث وتحقق من الحالة والمبلغ والعملة والدفع المثبت. حوّل المرجع الموثق إلى نفس الصيغة المعيارية التي يستخدمها V2.
2. عند إعادة محاولة طلب سبق اعتماده، أعد النتيجة المثبتة فقط إذا طابق سجل الحجز المرجع والشراء.
3. نفّذ `perform vx_sub_v2.claim_legacy_payment(v_canonical_key, v_purchase_ref);` داخل دالة الاعتماد، ثم نفّذ تحديث حالة الشراء والمنح القديمة في المعاملة نفسها. اترك تعارض التفرد يفشل المعاملة كاملة.
4. اربط زر اعتماد `aSetPurchase` بالـRPC بعد تثبيت توقيعه، وأغلق المسارات المباشرة الأخرى التي تمنح صلاحية الدفع. افصل الرفض والتعديلات الإدارية العادية بعد مراجعة استخدامها. طابق تاريخ الدفعات قبل فتح المسارين معاً.

## Telegram وTradingView

`provider-revocation.mjs` ينفذ السحب فقط إذا أعاد قارئ موثوق، لنفس الحساب والمورد والإصدار، نفياً صريحاً للمصادر الثلاثة: اشتراك قديم وحق مدى الحياة وV2. النقص أو تغير الإصدار يحتفظ بالوصول للمراجعة. `desired_access` القادم من 002 يقيس V2 فقط. حتى يتوفر قارئ المصادر الثلاثة، تبقى عمليات السحب معطلة. يحتاج العامل إلى إعادة القراءة وتنسيق السحب مع جميع كتّاب الحقوق للمورد نفسه، وتسجيل النتيجة ومطابقة الوصول بعد أخطاء المزود. لا يوجد عامل مزود مربوط في هذه الحزمة.

## الاختبار والتفعيل

- من جذر المشروع، شغّل `node --test tests/design/vexora-subscriptions-v2.test.mjs tests/subscriptions-v2/*.test.mjs`. يعمل الاختبار دون اتصال، ومجموعة PostgreSQL معلّقة افتراضياً.
- على عنقود اصطناعي محلي منفصل باسم `vexora-subscriptions-fixture` وقاعدة `vx_sub_test` ودور الاختبار `vx_test_admin`، اضبط `VX_SUB_TEST_PORT` إلى منفذ العنقود من 56000 إلى 56999 و`VX_SUB_RUN_POSTGRES=1`. بعدها شغّل `node --test tests/subscriptions-v2/postgres.test.mjs`. يدعم المشغل `VX_SUB_TEST_PSQL` لمسار psql. استخدم قاعدة اختبار جديدة لكل دورة تطبيق. لا تستخدم سلسلة اتصال Supabase.
- طبّق خطة التفعيل والتراجع المعتمدة في README بعد مطابقة السياسات والحقوق. حظر اعتماد الدفعات أثناء تعبئة سجل المطابقة. ابدأ بفحص ظلّي، بعدها افتح مجموعة صغيرة، ووسّع بعد اجتياز فحوص الدفع والوصول. عند التراجع أوقف الاعتمادات الجديدة والسحب الخارجي واحتفظ بسجل التسويات والحقوق المثبتة.

## المطلوب من المالك

1. الصق ملف الجرد فقط في Supabase SQL Editor وشغّله يدوياً، ثم شارك نتيجة JSON بعد مراجعتها.
2. شارك مقتطفات منقحة من **تعريفات** اعتماد الدفع القديم والمشغلات المؤثرة، وسياسات `purchases` و`storage.objects` والموارد المدفوعة. احذف أي قيم سرية أو روابط خاصة. إن لم يظهر مسار في الجرد فاذكر اسمه.
3. أكّد أسماء الحاويات الخاصة، وربط الخطط القديمة ومشتريات مدى الحياة بالدورات ومزايا Telegram وTradingView، وصيغة مرجع الدفع الفريد لكل قناة. يكفي وصف القاعدة وأمثلة اصطناعية.
